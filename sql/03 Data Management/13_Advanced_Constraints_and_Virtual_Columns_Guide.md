# Oracle Advanced Constraints and Virtual Columns Guide

## Quick Sheet

- **Deferrable constraint** = Constraint checked at commit instead of every statement.
- **Cascading foreign key** = Child rows react automatically to parent changes.
- **Enabled constraint** = Rule is currently enforced.
- **Validated constraint** = Existing data has been checked.
- **Virtual column** = Value calculated from other columns instead of stored directly.
- **Generated column** = Database-generated value based on an expression or identity rule.

## 1. Why Do We Need Advanced Constraints?

### The Problem: Basic Rules Do Not Cover Every Workflow

Bulk loads, circular references, and derived values may need more flexible integrity controls.

**Problems:**
- Valid data may arrive in dependency order that does not match parent-first insertion.
- Existing legacy data may need migration before validation.
- Derived values can become inconsistent when stored manually.

### The Solution: Advanced Constraint Features

Oracle supports delayed validation, controlled cascading, and calculated columns.

## 2. What Are Constraint States?

### Enabled and Disabled

```sql
ALTER TABLE employees ENABLE CONSTRAINT fk_emp_dept;
ALTER TABLE employees DISABLE CONSTRAINT fk_emp_dept;
```

### Validated and Novalidated

```sql
ALTER TABLE employees
ENABLE NOVALIDATE CONSTRAINT fk_emp_dept;
```

`ENABLE NOVALIDATE` enforces the rule for new changes without checking all existing rows.

### Why It Matters

This is useful during migrations, but existing invalid data must be tracked and cleaned up.

---

**➡ Transition:** Deferrable constraints move validation from statement time to transaction commit.

## 3. Deferrable Constraints

### The Challenge

Two related rows may need to be inserted in an order that temporarily violates a relationship.

### How It Works

```sql
CREATE TABLE child_table (
    child_id NUMBER PRIMARY KEY,
    parent_id NUMBER,
    CONSTRAINT fk_child_parent
        FOREIGN KEY (parent_id)
        REFERENCES parent_table(parent_id)
        DEFERRABLE INITIALLY DEFERRED
);
```

The constraint is checked when the transaction commits.

### Change Timing

```sql
SET CONSTRAINTS fk_child_parent IMMEDIATE;
SET CONSTRAINTS fk_child_parent DEFERRED;
```

### Use Case

Complex batch operations with temporary dependency ordering issues.

---

**➡ Transition:** Parent deletion behavior is controlled with cascading foreign keys.

## 4. Cascading Foreign Keys

### The Challenge

Deleting a parent row may leave child rows that no longer have a valid reference.

### How It Works

```sql
CREATE TABLE orders (
    order_id NUMBER PRIMARY KEY,
    customer_id NUMBER,
    CONSTRAINT fk_order_customer
        FOREIGN KEY (customer_id)
        REFERENCES customers(customer_id)
        ON DELETE CASCADE
);
```

Deleting a customer also deletes related orders.

### Set Null Alternative

```sql
FOREIGN KEY (manager_id)
REFERENCES employees(employee_id)
ON DELETE SET NULL
```

### Warning

Cascades can delete large amounts of data. They must match the business rule.

## 5. Virtual and Generated Columns

### Virtual Column

```sql
CREATE TABLE orders (
    quantity NUMBER,
    unit_price NUMBER,
    total_amount NUMBER GENERATED ALWAYS AS (quantity * unit_price) VIRTUAL
);
```

Oracle calculates the value when queried.

### Identity Column

```sql
CREATE TABLE employees (
    employee_id NUMBER GENERATED BY DEFAULT AS IDENTITY,
    first_name VARCHAR2(50)
);
```

The database generates identifiers automatically.

### Benefits

- Prevents repeated calculation logic
- Keeps derived values consistent
- Reduces application-side duplication

## 6. Comparison Matrix

| Feature | Purpose | Main Risk |
| --- | --- | --- |
| DEFERRABLE | Delay constraint checking | Errors appear at commit |
| ENABLE NOVALIDATE | Enforce new data only | Old invalid rows remain |
| ON DELETE CASCADE | Remove dependent rows | Large accidental deletion |
| Virtual column | Calculate derived value | Expression complexity |
| Identity column | Generate key automatically | Sequence behavior assumptions |

---

## 7. Best Practices

### 1. Use deferrable constraints only for real dependency requirements

### 2. Review child-row impact before enabling CASCADE

### 3. Prefer generated columns for deterministic derived values

**Why:** One database expression is safer than duplicated application calculations.

---

## 8. Common Mistakes

### Mistake 1: Assuming NOVALIDATE cleans old data

**Solution:** It only enforces the rule for future changes.

### Mistake 2: Using CASCADE without impact analysis

**Solution:** Test parent deletion with realistic child data.

### Mistake 3: Storing a value that can be calculated reliably

**Solution:** Consider a virtual or generated column.

## 9. Interview Q&A

**Q: What is a deferrable constraint?**
A: It is a constraint whose validation can be postponed until transaction commit.

**Q: What does ENABLE NOVALIDATE mean?**
A: New changes are checked, but existing rows are not revalidated.

**Q: What is a virtual column?**
A: A column calculated from an expression instead of independently stored data.

---

## 10. Revision Summary

- **DEFERRABLE** → check at commit
- **NOVALIDATE** → do not scan existing data
- **CASCADE** → remove dependent rows
- **SET NULL** → clear child reference
- **VIRTUAL** → calculated column
- **IDENTITY** → generated key

### Important Syntax

```sql
ALTER TABLE employees ENABLE NOVALIDATE CONSTRAINT fk_emp_dept;

CREATE TABLE order_items (
    quantity NUMBER,
    unit_price NUMBER,
    total_amount NUMBER GENERATED ALWAYS AS (quantity * unit_price) VIRTUAL
);
```
