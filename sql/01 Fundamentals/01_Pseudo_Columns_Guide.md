# SQL Pseudo Columns Guide

## Quick Sheet

- **Pseudo columns** = Virtual columns that provide metadata about rows or sessions (not actually stored in the table).
- **ROWNUM** = Sequential counter assigned **before** ORDER BY. Use for limiting results quickly.
- **ROWID** = Physical address of a row in the database. Unique per row. May change with TRUNCATE/ALTER.
- **SYSDATE** = Current date/time (no fractional seconds).
- **SYSTIMESTAMP** = Current date/time with fractional seconds and timezone.
- **USER** = Current database user name.
- **UID** = Current session numeric identifier.
- **LEVEL** = Hierarchy level in CONNECT BY queries (for tree structures).
- **Interview tip:** ROWNUM is tricky (assigned before ORDER BY). Use ROW_NUMBER() for proper ranking.

## 1. Why Do We Need Pseudo Columns?

### The Problem

When you query a table, you get data stored in columns. But sometimes you need **metadata about the data**, not the data itself:

```sql
SELECT first_name, salary FROM employees;
-- Output: first_name, salary
-- Missing: Which row is this? When was this retrieved? Who ran this query?
```

SQL has no built-in way to answer:
- "What is the row sequence number?" (1st row, 2nd row, etc.)
- "Where physically is this row stored?"
- "What is the current date and time?"
- "Who is the logged-in user?"

### The Solution: Pseudo Columns

**Pseudo columns** are virtual columns that Oracle provides **automatically** without storing them in the table:

```sql
SELECT ROW_NUMBER() OVER (ORDER BY salary) AS sequence,
       ROWID,
       SYSDATE,
       USER,
       first_name,
       salary
FROM employees;
-- Now we have metadata + data
```

Pseudo columns let you access system information as if they were regular table columns.

## 2. What Are Pseudo Columns?

### Definition

**Pseudo columns** are columns that:
- Appear like regular columns in SELECT statements
- Are **NOT physically stored** in the table
- Provide **metadata** about rows or the session
- Are automatically maintained by Oracle

### Key Differences: Pseudo Column vs Real Column

| Aspect | Real Column | Pseudo Column |
| --- | --- | --- |
| **Storage** | Stored in table | Generated on-the-fly |
| **Updatable** | Can UPDATE | Cannot UPDATE |
| **Space** | Uses disk space | Uses no space |
| **Refresh** | Manual updates | Auto-generated each query |

### Example

```sql
-- Real columns (stored in employees table)
SELECT employee_id, first_name, salary FROM employees;
-- All three are physically stored on disk

-- Pseudo columns (generated by Oracle)
SELECT ROWNUM, ROWID, SYSDATE, first_name FROM employees;
-- ROWNUM, ROWID, SYSDATE are NOT stored; Oracle generates them
```

### Why Oracle Provides Pseudo Columns

Pseudo columns solve problems without adding storage overhead:
- No need to store row numbers (ROWNUM)
- No need to store row addresses (ROWID)
- No need to duplicate the current time for each row (SYSDATE)

## 3. ROWNUM (Sequential Counter)

### What is ROWNUM?

**ROWNUM** is a pseudo column that assigns a **sequential number** to each row **as Oracle returns it from the query**.

```sql
SELECT ROWNUM, employee_id, first_name, salary FROM employees;
```

**Output:**
```
ROWNUM  EMPLOYEE_ID  FIRST_NAME  SALARY
------  -----------  ----------  ------
1       101          Steven      24000
2       102          Neena       17000
3       103          Alexander   17000
4       104          Bruce       6000
5       105          David       4800
...
```

### Critical Point: ROWNUM is Assigned BEFORE ORDER BY

This is the **tricky** part of ROWNUM:

```sql
SELECT ROWNUM, first_name, salary
FROM employees
WHERE ROWNUM <= 5
ORDER BY salary DESC;
```

**Flow:**
```
Step 1: Oracle fetches first 5 rows (ROWNUM = 1,2,3,4,5)
Step 2: Oracle applies ORDER BY salary DESC
Result: ROWNUM is still 1-5, but salary is now sorted!
```

**Output might be:**
```
ROWNUM  FIRST_NAME  SALARY
------  ----------  ------
1       Steven      24000   ← ROWNUM 1 happens to be highest salary
3       Alexander   17000   ← ROWNUM 3 assigned, but it's 2nd when sorted
2       Neena       17000   ← ROWNUM 2 assigned, but it's 3rd when sorted
...
```

**The problem:** ROWNUM looks random after sorting because it was assigned **before** the ORDER BY!

### Common Use Case: Get First N Rows (Without Sorting)

```sql
SELECT ROWNUM, first_name, salary
FROM employees
WHERE ROWNUM <= 10;
-- Gets first 10 rows (in insertion order, not sorted)
```

This is fast because Oracle doesn't need to sort—just return the first 10 rows and stop.

### Important: WHERE ROWNUM >= N Doesn't Work

```sql
-- ❌ WRONG: This returns no rows!
SELECT * FROM employees WHERE ROWNUM >= 5;

-- Why? ROWNUM is assigned as Oracle returns rows.
-- Row 1 is returned → ROWNUM = 1 (not >= 5, filtered out)
-- Row 2 is returned → ROWNUM = 2 (not >= 5, filtered out)
-- ...never reaches row 5, never gets ROWNUM = 5
```

**Workaround:** Use a subquery:
```sql
-- ✅ CORRECT
SELECT * FROM (
  SELECT ROWNUM AS rn, employees.* FROM employees
)
WHERE rn >= 5;
-- Now ROWNUM is calculated in subquery, then filtered
```

---

**➡ Transition:** ROWNUM has limitations because it's assigned before sorting. When you need **proper ranking after sorting**, use **ROW_NUMBER()** instead.

## 4. ROWNUM vs ROW_NUMBER()

### The Problem with ROWNUM

ROWNUM is assigned **before** ORDER BY, leading to confusing results:

```sql
SELECT ROWNUM, first_name, salary FROM employees ORDER BY salary DESC;
-- ROWNUM doesn't match the sorted order
-- Confusing!
```

### The Solution: ROW_NUMBER()

**ROW_NUMBER()** is an **analytic function** (not a pseudo column) that assigns row numbers **after** sorting:

```sql
SELECT ROW_NUMBER() OVER (ORDER BY salary DESC) AS rank,
       first_name,
       salary
FROM employees;
```

**Output:**
```
RANK  FIRST_NAME  SALARY
----  ----------  ------
1     Steven      24000   ← Rank 1 is highest salary
2     Neena       17000   ← Rank 2 is second highest
3     Alexander   17000   ← Rank 3 is third
4     Bruce       6000
...
```

### Key Differences

| Aspect | ROWNUM | ROW_NUMBER() |
| --- | --- | --- |
| **When assigned** | Before ORDER BY | After ORDER BY |
| **Result** | Looks random after sorting | Matches sorted order |
| **Use case** | Get first N rows fast | Proper ranking, pagination |
| **Type** | Pseudo column | Analytic function |

### Comparison Example

Same query, different results:

**Using ROWNUM:**
```sql
SELECT ROWNUM, first_name, salary FROM employees ORDER BY salary DESC FETCH FIRST 3 ROWS ONLY;
-- ROWNUM might be 5, 1, 12 (whatever those rows were originally)
```

**Using ROW_NUMBER():**
```sql
SELECT ROW_NUMBER() OVER (ORDER BY salary DESC), first_name, salary FROM employees FETCH FIRST 3 ROWS ONLY;
-- ROW_NUMBER will be 1, 2, 3 (matching the sort order)
```

### Interview Insight

When asked about ranking or pagination, always recommend **ROW_NUMBER()** over ROWNUM. ROWNUM is outdated for these use cases.

## 5. ROWID (Physical Address)

### What is ROWID?

**ROWID** is a pseudo column that contains the **unique physical address** of a row in the database.

```sql
SELECT ROWID, employee_id, first_name FROM employees;
```

**Output:**
```
ROWID                EMPLOYEE_ID  FIRST_NAME
-------------------  -----------  ----------
AAAOLeAAEAAAABGAAA  101          Steven
AAAOLeAAEAAAABGAAB  102          Neena
AAAOLeAAEAAAABGAAC  103          Alexander
...
```

Each ROWID uniquely identifies the physical block and slot where the row is stored.

### ROWID Format

The ROWID string contains:
- **Block number** (where on disk the row is)
- **Row number** (which slot within that block)
- **File number** (which datafile)

Example: `AAAOLeAAEAAAABGAAA`
- `AAAOL` = Object number (table identifier)
- `e` = Relative file number
- `AAAA` = Block number
- `AA` = Row number

### Key Advantage: Fast Lookups

ROWID is the fastest way to access a row because it's a direct pointer:

```sql
-- Very fast: Direct lookup
SELECT * FROM employees WHERE ROWID = 'AAAOLeAAEAAAABGAAA';

-- Slower: Must scan and filter
SELECT * FROM employees WHERE employee_id = 101;
```

Indexes internally use ROWID for this reason.

### Uniqueness

ROWID is **unique within a table**:
- No two rows in the same table share a ROWID
- Different tables can have identical ROWID values
- When comparing ROWIDs, always specify the table context

---

**➡ Transition:** ROWID is unique and permanent for a given row—but does it **ever change**? That's an important distinction.

---

## 6. Does ROWID Change?

### Short Answer

ROWID usually stays the same, but **can change** with certain DDL operations.

### Detailed Answer

#### DML Operations (INSERT, UPDATE, DELETE) → ROWID Stays Same

```sql
-- DML: ROWID does NOT change
INSERT INTO employees VALUES (...);     -- New row gets new ROWID
UPDATE employees SET salary = 50000 ... -- ROWID stays same
DELETE FROM employees WHERE ...         -- ROWID released if row deleted
```

A row's ROWID remains constant as long as the row exists. Updating data doesn't move the row physically.

#### DDL Operations (TRUNCATE, ALTER) → ROWID MAY Change

```sql
-- TRUNCATE: Table reorganized, ROWID changes
TRUNCATE TABLE employees;
INSERT INTO employees VALUES (...);
-- The inserted row may have a different ROWID than before

-- ALTER TABLE: May cause reorganization
ALTER TABLE employees MOVE;
-- ROWIDs may change after reorganization
```

#### Deleted and Reinserted Rows → ROWID Changes

```sql
-- Delete a row
DELETE FROM employees WHERE employee_id = 101;
-- ROWID 'AAAOLeAAEAAAABGAAA' is now available for reuse

-- Reinsert the row
INSERT INTO employees VALUES (101, ...);
-- New ROWID assigned (might be different physical location)
```

### Why ROWID Changes Matter

**Don't store ROWID in another table expecting it to be permanent:**

```sql
-- ❌ RISKY
CREATE TABLE saved_rowids AS
SELECT employee_id, ROWID FROM employees;

-- Later, after TRUNCATE and reinsertion:
SELECT * FROM employees WHERE ROWID = saved_rowid;  -- Might get wrong row!
```

**Use primary keys instead:**

```sql
-- ✅ SAFE
CREATE TABLE saved_ids AS
SELECT employee_id FROM employees;

SELECT * FROM employees WHERE employee_id IN (SELECT employee_id FROM saved_ids);
```

## 7. SYSDATE and SYSTIMESTAMP

### SYSDATE (Current Date and Time)

**SYSDATE** returns the current date and time from the database server.

```sql
SELECT SYSDATE FROM DUAL;
-- Output: 28-JUL-2026 14:35:22
```

### SYSTIMESTAMP (Current Date, Time, and Timezone)

**SYSTIMESTAMP** includes fractional seconds and timezone information:

```sql
SELECT SYSTIMESTAMP FROM DUAL;
-- Output: 28-JUL-26 14.35.22.123456 +00:00
```

### When to Use Which

| Pseudo Column | Use Case |
| --- | --- |
| **SYSDATE** | Date-only queries, simple timestamps, backward compatibility |
| **SYSTIMESTAMP** | Precision timing, timezone-aware applications, high-frequency transactions |

### Examples

```sql
-- Get current date
SELECT SYSDATE FROM DUAL;

-- Store current timestamp in a column
INSERT INTO audit_log VALUES (emp_id, action, SYSDATE);

-- Add time intervals
SELECT SYSDATE + 7 AS next_week FROM DUAL;

-- Get fractional seconds for precise timing
SELECT SYSTIMESTAMP FROM DUAL;
```

## 8. USER and UID

### USER (Current Database User)

**USER** returns the name of the currently logged-in database user.

```sql
SELECT USER FROM DUAL;
-- Output: SCOTT (or whatever user is logged in)
```

### UID (Session Identifier)

**UID** returns the numeric identifier of the current session.

```sql
SELECT UID FROM DUAL;
-- Output: 32 (or whatever the session ID is)
```

### Common Uses

**User tracking in audit tables:**
```sql
INSERT INTO audit_table VALUES (emp_id, action, USER, SYSDATE);
-- Records who made the change and when
```

**User-based security:**
```sql
SELECT * FROM employee_salary WHERE USER = 'HR_MANAGER'
UNION ALL
SELECT * FROM employee_salary WHERE created_by = USER;
-- Employees see only their own salary; HR sees all
```

### Difference: USER vs UID

- **USER** = Name (human-readable)
- **UID** = Number (internally unique, but changes each session)

## 9. LEVEL (Hierarchical Queries)

### What is LEVEL?

**LEVEL** is a pseudo column used in **hierarchical queries** (queries that walk tree structures like organizational charts).

**LEVEL** indicates the depth of a node in the tree:
- **LEVEL 1** = Root node (top of hierarchy)
- **LEVEL 2** = Direct children of root
- **LEVEL 3** = Grandchildren, etc.

### Organizational Hierarchy Example

**Data structure (Manager relationships):**
```
Steven (ID=100, Manager=NULL) ← Root, LEVEL 1
├── Neena (ID=102, Manager=100) ← LEVEL 2
│   ├── Alexander (ID=103, Manager=102) ← LEVEL 3
│   └── Bruce (ID=104, Manager=102) ← LEVEL 3
├── David (ID=105, Manager=100) ← LEVEL 2
│   └── Peter (ID=106, Manager=105) ← LEVEL 3
```

### CONNECT BY Query

```sql
SELECT employee_id,
       first_name,
       manager_id,
       LEVEL AS hierarchy_level,
       LPAD(' ', (LEVEL-1)*2) || first_name AS indent_name
FROM employees
START WITH manager_id IS NULL        -- Start from CEO (no manager)
CONNECT BY PRIOR employee_id = manager_id;  -- Employee ID links to Manager ID
```

**Output:**
```
EMPLOYEE_ID  FIRST_NAME  LEVEL  INDENT_NAME
-----------  ----------  -----  -----------
100          Steven      1      Steven
102          Neena       2        Neena
103          Alexander   3          Alexander
104          Bruce       3          Bruce
105          David       2        David
106          Peter       3          Peter
```

### How CONNECT BY Works

1. **START WITH:** Find the root node(s) (CEO with no manager)
2. **CONNECT BY:** Define the parent-child relationship (Employee connects to Manager)
3. **PRIOR:** Reference the parent row in the connection
4. **LEVEL:** Automatically assigned based on depth

### Practical Uses

**Find all employees under a specific manager:**
```sql
SELECT * FROM employees
START WITH employee_id = 100
CONNECT BY PRIOR employee_id = manager_id;
-- Returns Steven and all his direct/indirect reports
```

**Find all managers above a specific employee:**
```sql
SELECT * FROM employees
START WITH employee_id = 103
CONNECT BY PRIOR manager_id = employee_id;
-- Returns Alexander, Neena, Steven (chain up to CEO)
```

## 10. Best Practices

### 1. Use ROW_NUMBER() Over ROWNUM for Ranking

**Avoid:**
```sql
SELECT ROWNUM, first_name, salary FROM employees ORDER BY salary DESC;
-- ROWNUM doesn't match sort order
```

**Prefer:**
```sql
SELECT ROW_NUMBER() OVER (ORDER BY salary DESC) AS rank, first_name, salary FROM employees;
-- Proper ranking
```

---

### 2. Use ROWID for Direct Lookups, Not Storage

**Avoid:**
```sql
-- Storing ROWID for later use (risky after DDL)
CREATE TABLE saved_rows AS SELECT employee_id, ROWID FROM employees;
```

**Prefer:**
```sql
-- Use primary keys
CREATE TABLE saved_employees AS SELECT employee_id, first_name FROM employees;
```

---

### 3. Use SYSDATE or SYSTIMESTAMP Consistently

**Avoid mixing:**
```sql
INSERT INTO audit_log VALUES (..., SYSDATE);
INSERT INTO audit_log VALUES (..., SYSTIMESTAMP);
-- Inconsistent precision
```

**Prefer:**
```sql
-- Choose one and stick with it
INSERT INTO audit_log VALUES (..., SYSDATE);
-- Or for high precision:
INSERT INTO audit_log VALUES (..., SYSTIMESTAMP);
```

---

### 4. User Tracking for Audits

```sql
-- Track who made changes
INSERT INTO audit_log VALUES (
  employee_id,
  'INSERT',
  USER,
  SYSDATE
);
```

---

### 5. Master CONNECT BY for Hierarchical Queries

Practice hierarchical queries because they're common in interviews:

```sql
SELECT *
FROM employees
START WITH manager_id IS NULL
CONNECT BY PRIOR employee_id = manager_id
ORDER BY LEVEL;
```

## 11. Common Mistakes

### Mistake 1: Using ROWNUM for Ranking After ORDER BY

```sql
-- ❌ WRONG
SELECT ROWNUM AS rank, first_name, salary FROM employees ORDER BY salary DESC;
-- ROWNUM looks random

-- ✅ CORRECT
SELECT ROW_NUMBER() OVER (ORDER BY salary DESC) AS rank, first_name, salary FROM employees;
```

---

### Mistake 2: Filtering with ROWNUM >= N

```sql
-- ❌ WRONG (returns nothing)
SELECT * FROM employees WHERE ROWNUM >= 5;

-- ✅ CORRECT
SELECT * FROM (SELECT ROWNUM AS rn, employees.* FROM employees) WHERE rn >= 5;
```

---

### Mistake 3: Relying on ROWID After Reorganization

```sql
-- ❌ RISKY
SELECT ROWID FROM employees;
-- Save ROWID somewhere
ALTER TABLE employees MOVE;  -- ROWID may change!
-- ROWID is no longer valid
```

---

### Mistake 4: Forgetting START WITH in CONNECT BY

```sql
-- ❌ INCOMPLETE
SELECT * FROM employees CONNECT BY PRIOR employee_id = manager_id;
-- Where does the hierarchy start?

-- ✅ COMPLETE
SELECT * FROM employees
START WITH manager_id IS NULL
CONNECT BY PRIOR employee_id = manager_id;
```

---

### Mistake 5: Mixing SYSDATE and SYSTIMESTAMP

```sql
-- ❌ INCONSISTENT
SELECT SYSDATE FROM table1
UNION ALL
SELECT SYSTIMESTAMP FROM table2;
-- Different data types, may cause issues
```

## 12. Interview Q&A

### Conceptual

**Q: What's the difference between ROWNUM and ROW_NUMBER()?**

A:
- **ROWNUM:** Assigned before ORDER BY (looks random after sorting).
- **ROW_NUMBER():** Assigned after ORDER BY (matches sort order).

---

**Q: Why does WHERE ROWNUM >= 5 return no rows?**

A: ROWNUM is assigned as rows are returned. Row 1 gets ROWNUM=1 (not >=5, filtered), Row 2 gets ROWNUM=2 (not >=5, filtered), etc. Never reaches a row with ROWNUM >=5.

---

**Q: What is ROWID used for?**

A: Direct row access. It's the physical address of the row. Indexes use ROWID internally for fast lookups.

---

### Comparison

**Q: SYSDATE vs SYSTIMESTAMP?**

A:
- **SYSDATE:** Date and time, lower precision.
- **SYSTIMESTAMP:** Date, time, fractional seconds, and timezone.

---

**Q: ROWID vs primary key?**

A:
- **ROWID:** Physical address, may change with DDL, not stored.
- **Primary key:** Logical identifier, permanent, stored as data.

---

### Scenario

**Q: You need to limit results to first 10 rows in sorted order. Use ROWNUM or ROW_NUMBER()?**

A: **ROW_NUMBER().** ROWNUM is assigned before ORDER BY, so it wouldn't give you the first 10 in sorted order.

---

**Q: You have a hierarchical org chart. How do you find all employees under a specific manager?**

A: Use CONNECT BY:
```sql
SELECT * FROM employees
START WITH employee_id = manager_id_value
CONNECT BY PRIOR employee_id = manager_id;
```

## 13. Revision Summary

### 1-Minute Revision

**Pseudo Columns = Virtual metadata columns**

1. **ROWNUM:** Sequential counter assigned before ORDER BY (not for ranking).
2. **ROW_NUMBER():** Proper ranking assigned after ORDER BY.
3. **ROWID:** Physical address of a row. Fast lookups but may change with DDL.
4. **SYSDATE:** Current date/time.
5. **SYSTIMESTAMP:** Current date/time with fractional seconds and timezone.
6. **USER:** Current database user name.
7. **UID:** Session numeric identifier.
8. **LEVEL:** Depth in hierarchical queries (CONNECT BY).
9. **Interview trap:** ROWNUM assigned before ORDER BY → use ROW_NUMBER() instead.

### Interview Keywords

- Pseudo columns (virtual, auto-generated)
- ROWNUM assigned before ORDER BY
- ROW_NUMBER() assigned after ORDER BY
- ROWID (physical address, unique)
- SYSDATE, SYSTIMESTAMP (precision difference)
- USER, UID (audit tracking)
- LEVEL (hierarchical queries)
- CONNECT BY, START WITH (hierarchy navigation)

### Important Syntax

```sql
-- ROWNUM (first N rows, fast)
SELECT ROWNUM, * FROM employees WHERE ROWNUM <= 10;

-- ROW_NUMBER (proper ranking)
SELECT ROW_NUMBER() OVER (ORDER BY salary DESC) AS rank, * FROM employees;

-- ROWID (direct lookup)
SELECT * FROM employees WHERE ROWID = 'AAAOLeAAEAAAABGAAA';

-- SYSDATE, SYSTIMESTAMP
SELECT SYSDATE, SYSTIMESTAMP FROM DUAL;

-- USER tracking
INSERT INTO audit_log VALUES (emp_id, action, USER, SYSDATE);

-- LEVEL (hierarchy)
SELECT *, LEVEL FROM employees
START WITH manager_id IS NULL
CONNECT BY PRIOR employee_id = manager_id;
```
